## 4. 数据、使用范围与划分

### 4.1 样例来源与字段

由用户选择历史对话中的本人表达，或亲自对场景作答。AI 生成的“像用户的话”不冒充真实样例。AI 可辅助整理标签和规则，但用户必须确认内容准确及用途。

每组开发样例至少记录：

| 字段 | 要求 |
| --- | --- |
| sampleId | 本地稳定编号，如 D001；不含真实姓名 |
| source | 真实历史、本人现场作答、本人对实际回复的改写 |
| relationship | 熟朋友、普通朋友或用户明确指定的其他关系 |
| scenario / context | 场景及必要前文，尽量去除姓名、联系方式、敏感事实 |
| partnerInput | 对方来话，只作为理解背景 |
| creatorReply | 用户本人的回复，作为表达目标 |
| reason / boundary | 用户对接话方式、分寸的说明，可为空，不能由模型伪称用户意见 |
| allowedUse | 仅本地分析，或允许进入将来给朋友的角色包 |
| split | 开发、开发验证、封存评价 |

只把本人回复当作模仿目标。不得把对方措辞混入用户风格，不根据项目沟通习惯自动推断日常口吻。

### 4.2 初始数据规模

- 开发素材：目标 30 组，用户愿意时可增加到 50 组；小于 30 组时可以做模板演示，但正式对照前先记录数据不足，不宣称完成本阶段。
- 开发验证：6 个新场景，供用户看结果、指出问题和最多一次配置修订。
- 封存评价：12 个新单轮场景，不参与规则提炼、选例或配置修改。
- 多轮评价：2 段预先写好的三轮用户输入，一段日常接话、一段拒绝／分歧／不知道事实等边界场景。

覆盖问候、进展、疲惫或烦躁、安慰、玩笑、拒绝、分歧、忙时回应和不知道的信息。至少含两种关系类型。封存题中至少两题检查不知道事实时的表达，至少两题检查关系分寸。题目具体文字由用户提供或确认，PLAN 不预先给出“像用户”的标准答案。

### 4.3 防止评估资料混入调教

按完整对话、相近事件和近似问题分组。相邻句或同题改写不能随机分到开发与封存集合。

12 个正式单轮场景和 2 段正式多轮对话均属于封存资料，包括多轮的全部用户输入、参考回复及期望表现。先完成开发资料和 B／C 配置，再由用户提交这些输入；本人参考回复及期望可先自行写好并单独保管，待模型输出全部保存后用于评价。03 不主动读取参考文件来调规则。封存输入及答案不进入两条正例，也不加入自动或人工逐题选例。

正式评价中不点“我会这样说”。该操作会把测试题及改写写进草稿。纠正意见先进入私有旁表；正式评价结束后，若用于下一轮调教，该题转为开发题，下一轮另保留未见过的验收题。

## 6. 提示预算、启动保护与留证方式

### 6.1 2048 字符限制

当前 numCtx=4096 时，service.ts 传入的 maxPromptChars 为 2048。该值按 JavaScript UTF-16 单位计算，不是 token。共通规则、角色 JSON、输入、历史和记忆都计入。

现有发布只用“你好。”检查最小提示。发布成功不能证明其他输入、记忆或多轮历史一定放得下。

冻结前，用相同提交的 buildMessages 对开发题及虚构的多轮长度占位做预检，不读取正式多轮原题。配置冻结后再接收全部封存输入，只检查能否构造，不用其参考答案或原题改配置。正式多轮每次发送前按本组真实已有历史重新核对预算。需记录：

- 配置、角色版本和文件摘要；
- caseId、输入内容和模型参数；
- characterCount；
- 入选记忆 ID、遗漏历史及记忆数；
- 固定正例 ID。

单轮主对照为空历史、空记忆，遗漏应为 0。多轮中若裁剪历史，记录裁剪范围，不宣称模型看到了被裁掉的内容；不临时扩预算来使结果过关。

正式题超限时记为该配置的技术失败，保留题目，不能剔除难题或当场改角色。需要修订时终止该冻结配置的正式评价，另提变更和新的评价安排。

### 6.2 每次启动的检查

沿用上阶段已审 RUNBOOK 的保护方法，调整为本阶段新目录，并留存实际执行文本：

1. 新终端仅设置进程级 PATH 和运行变量，固定 Node／Electron 路径，核对版本。
2. 为本轮明确建立 creator、arm-a、arm-b、arm-c，及需要时的 recipient 数据目录。
3. 每次创建应用进程前，在同一启动函数中检查 ORANGE_CAT_DATA_DIR 等于当前组的预期绝对目录，目录存在且不指向默认业务库或历史验收库；缺失或不符时停止。
4. 模型服务核对 PID、启动时间、程序路径、版本、环回监听和禁云日志；已有不明服务占用 11434 时保留并报告，不结束它。
5. 启动后从真实窗口或应用状态读回数据库路径、人格版本与模型。
6. 组间切换先关闭上一应用，不能以不明窗口、浏览器预览或残留进程充当本组结果。

辅助脚本只管理其本次启动且归属明确的进程。不得修改永久 PATH 或整个系统配置。

### 6.3 原始证据与重建证据

现有评估导出缺少完整人格、全部参数和提示正文，因此每组必须配角色 JSON、固定环境／参数清单和 caseId—recordId 映射。

每条正式请求至少保存：

- runId、caseId、arm、角色 revision／SHA-256、模式；
- 本次代码提交、模型完整 digest、生成参数；
- 实际输入／输出与错误原文；
- 完整等待时间、输出 token 等现有指标；
- prompt 字符计数、记忆／历史遗漏；
- 尝试编号、是否技术重试及原因。

可以复用上阶段隔离取证适配器的方法，在应用到本机模型的调用处记录实际请求和响应；新增脚本仅在忽略目录，不能改写请求内容、伪造响应、转发到外部或跳过正常校验。先用虚构短输入证明取证不改变实际请求和返回，再用于正式语料。

若只能调用同提交函数重建预期提示，明确标“重建核对”，不可写成实际请求已捕获。正式 T05 的请求范围核验须有实际调用记录；无法取得时，T05 记为证据不足。重建结果可作辅助核对，不能替代本修订要求的实际调用证据；需要改变通过条件时，按第 12 节另作决定。

### 6.4 导出和清空顺序

每个独立单轮题从空历史开始；生成后先导出、核对文件可读及 recordId，再清空试聊。现有清空同时删除该朋友历史和评估。

多轮段落中不在中间清空，段落结束后统一导出，再清空。发布前先导出需要保留的评估；每个角色发布后立即导出，避免下一版本覆盖唯一可导出的当前版本。

正式评价中的纠正写私有旁表，不进入工作台草稿。

## 7. 实验顺序、调用数量与修订

### 7.1 开发对照

1. 完成开发资料审核、规则确认、A／B／C 构建和预算预检。
2. 对 6 个开发场景各运行 A／B／C 一次，共 18 次生成。
3. 匿名排列三组回答，用户指出像／不像和原因。
4. 最多进行一次 B／C 配置修订；B／C 仍保持“只差固定两条例子”的关系。使用同 6 题仅复测 B／C，共最多 12 次。
5. 根据开发反馈预选 B 或 C 为正式候选；记录用户选择和理由，冻结两组配置及所有文件摘要。

A 保留原基线，不为了配合结果而修改。若不需要修订，不执行额外 12 次。

### 7.2 封存单轮评价

候选和 B／C 配置冻结后，用户提供 12 个封存场景的输入。三组各答一次，共 36 次。题目中的关系与必要背景以同样文字送入三组，原参考回复不进入模型请求。

固定组运行顺序在记录中说明；先做各组的短热身并单独计数。速度报告包含实际条件，不把热身后的最短回复当整体性能。

每题生成一次。回答生硬、建议多、风格不像或事实错误，都保留原结果，不因质量差重抽。

### 7.3 短多轮评价

两段预先固定并封存的三轮用户输入，在配置冻结后才提供给执行者；A／B／C 各运行一次，共 18 次。各组使用相同的用户输入序列，保留本组真实回复历史，不把别组回复拷入上下文。

第二、三轮输入应承接用户已经给出的背景，不能假定模型上一轮必定给出某个特定答案。参考期待只用于用户评价，不进入模型请求；若固定输入在某组形成不合适语境，保留这一限制，不针对该组改题。

多轮用于观察风格回退、关系分寸、主体混淆及上下文裁剪。两段都作为正式评价，不在段落中途调规则或追加样例。

### 7.4 模拟接收检查

在独立 recipient 测试库中导入开发阶段预选的候选角色，保留自己的一条虚构短记忆。检查导出只含角色和模型配置，不含创建库朋友数据、开发资料、封存题或评价。

用最多 4 条短请求观察：自己的虚构记忆、其他档案不可用的信息、必要的分寸检查、重启后的候选与记忆读回。真实窗口确认数据库路径和角色版本。该步骤只在用户 Windows 上模拟接收，不发送给外部朋友，不代替 macOS 验证。

程序把其他朋友资料放入请求属于技术隔离失败；没有该资料却编造答案属于事实可靠性失败。二者分开记录。

### 7.5 上限与失败处理

| 用途 | 计划生成次数上限 |
| --- | ---: |
| 首轮开发 6×3 | 18 |
| 一次 B／C 修订复测 6×2 | 12 |
| 正式单轮 12×3 | 36 |
| 多轮 2×3×3 | 18 |
| 模拟接收 | 4 |
| 小计 | 88 |
| 热身、取证核验、运行故障重试 | 包含在总上限余量内 |
| 本阶段 /api/chat 尝试次数总上限 | 120 |

失败、取消和技术重试均计入 120；version／tags／show 等预检另记。不要用重启脚本清零计数。

每项只允许因明确运行故障进行一次技术重试，保存原失败及理由。主观质量差不是重试理由。达到上限、完成约定实验或发生无法保持隔离的故障，即停止新增生成并报告结果；增加实验范围需另作决定。

### 9.2 用户评价 U01–U03

本节编号仅属于 M0-PERSONA-STYLE，不替代上一阶段同名编号。

U01：用户确认风格资料与可分享范围，确认规则确实来自本人，选定两条可进入角色包的短例。

U02：每题把 A／B／C 回答随机排列为 X／Y／Z，保存随机种子及私有映射；不显示组名、角色版本和参数，不改写原回复。用户先完成下列匿名评分，评分固定后再揭示组名。对 12 题分别评价：

- 本人风格：0＝不像，1＝部分像，2＝我可能这样说。
- 自然程度：0＝明显生硬，1＝可以接受，2＝自然。
- 问题标记：多余建议、不合关系的亲密表达、无依据事实、样例事实移植、答非所问或强行猫化。
- 本题 X／Y／Z 哪个更像本人：给出排序，允许并列，不强迫每题选一个赢家。03 依据私有映射从用户的匿名排序计算候选相对 A 的“更像／相近／更不像”，不让用户在匿名评分阶段识别 A，也不由 03 代填偏好。

候选在开发阶段预选，不能看完封存结果后偷偷换成另一组来掩盖失败。若另一组更好，报告完整比较并由用户决定后续采用方向；不将封存结果反过来修改本轮配置。

本修订建议的阶段产品门槛：

1. 预选候选在 12 题中至少 8 题“本人风格”为 2。
2. 至少 10 题“自然程度”不低于 1。
3. 相对 A 至少 8 题更像，更不像的题不超过 2。
4. 不出现未经依据的现实共同经历、个人隐私事实编造或跨朋友资料泄漏；用户明确允许的角色虚构另行标注，不冒充现实。
5. 两段多轮整体体验均由用户认为可以继续采用。

这些是待批准的本阶段门槛，不是人格相似度百分比，也不保证达到“完整复刻本人”。

U03：用户体验普通窗口下的候选，评价完整等待时间和电脑使用感受。汇总中列出中位数、P90、最大值和实际样本数，冷启动／热身另列；用户此前接受的“五秒以内简单对话”作为体验参照，不由 03 换成未经同意的硬性性能门槛。

若 U02 或 U03 不接受，准确写“实验完成、风格／体验未达标”，整理失败类型。之后由 01 提出精简资料、调整共通提示、增加检索或微调等下一方案，不自动启动。
