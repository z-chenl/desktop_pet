## 3. 当前回复的问题来自哪里

### 3.1 截图能支持的观察

| 用户输入 | 截图中的现象 | 对后续工作的含义 |
| --- | --- | --- |
| 今天怎么样 | 回答在窗台晒太阳，主动表达“想你了”，邀请一起发呆 | 猫角色扮演和亲密程度都需要用户确认；尚无依据说明这是用户本人的表达习惯 |
| 我的验证饮料代号是什么 | 正确回答 LM_R_青梅，随后添加喝完分享感受、发现口味的建议 | 记忆读取成功与表达合适是两项判断；此处不需要自动延伸建议 |
| 我的小猫好调皮 | 回答自己偷吃零食，并说别让“它们”弄乱“我的小窝” | 强行把猫设定带入，并扩展了没有给出的场景和关系 |

截图可见 3.0 秒和 0.6 秒等单轮显示值，与用户对速度的描述相容；这些不是复杂任务性能测评。

### 3.2 仓库中的具体原因

当前默认人格明确写明是“虚构开发样例”，尚未代表 Chen 的真实说话习惯。其中包含“先回应对方眼前的感受，再给一个具体的小建议”的规则。该规则为多余建议提供了一个直接、可检查的来源，但没有单独对照试验，不能断言它是唯一原因。[默认人格源码](https://github.com/z-chenl/desktop_pet/blob/32f766ebb6826afb652a00887cab7e1b4aa8f4f4/packages/persona-core/src/persona.ts)

共通系统消息同时规定“你是一个通过文字与朋友互动的桌面橘猫”。通用对照和人格模式都使用这条共通设定。因此，现有“通用对照”也会受到猫身份影响，不等于完全没有角色设定的基座模型。[提示构造源码](https://github.com/z-chenl/desktop_pet/blob/32f766ebb6826afb652a00887cab7e1b4aa8f4f4/packages/persona-core/src/prompt.ts)

03 的证据说明 v1、v2 使用虚构样例，v2 增加一条修正。当前没有证据表明已经用用户本人的代表性日常对话完成风格校准。[实际人格验证记录](https://github.com/z-chenl/desktop_pet/blob/32f766ebb6826afb652a00887cab7e1b4aa8f4f4/docs/iterations/M0-LOCAL-MODEL/EVIDENCE.md)

### 3.3 需要分别解决的三个问题

1. **说话习惯：**如何用词、句子长短、是否打趣、何时追问、什么时候只回应一句。
2. **关系分寸：**对熟朋友、普通朋友的称呼、亲密程度和拒绝方式。
3. **事实依据：**只依据当前输入和获准记忆回答；不知道时不编造共同经历。

风格更像本人，不会自动保证事实正确。虚构的猫角色日常可以作为明确的角色表演设计，但不能冒充用户真实经历，也不应默认塞入每次聊天。

建议产品方向为：**橘猫承担形象和动作，表达方式来自用户确认的真实样例；猫语、猫窝和撒娇程度作为可调的角色表演选项。** 这是待用户审核的产品建议。

## 4. 网络研究：哪些案例值得借鉴

检索覆盖了开源项目、作者文档和原始论文。以下是代表性证据，不声称穷尽全网，也没有在用户设备上复现这些外部项目。

### 4.1 WeClone：最贴近私人聊天学习的工程案例

WeClone 提供聊天数据整理、SFT/LoRA 微调和推理流程。作者的微调说明同时坦言 7B 效果一般、结果受数据和模型规模影响；不能把演示效果当成当前 Qwen 4B 的效果保证。[官方微调文档](https://github.com/xming521/WeClone/blob/master/docs/en/finetune.md)

它的风格分析从本人发送的消息中提取用词、句式、标点、语气、互动节奏等特征，并提供不调用模型的本地统计选项。值得借鉴的是可核对的风格特征与数据整理方法。[官方风格分析说明](https://www.weclone.love/en/docs/profile/style)

当前新版画像功能使用 Codex 或兼容 API，免训练 agent clone 仍标为开发中。因此不建议直接替换现有工作台，更不能把整套默认流程标为“完全离线、必然零费用”。[当前官方 README](https://github.com/xming521/WeClone/blob/master/README_zh.md)

### 4.2 ChatHaruhi：按场景找相关对白

ChatHaruhi 结合角色设定和剧本中的人物记忆，论文报告在 32 个影视、动漫人物上做了角色扮演评估。[原论文](https://arxiv.org/abs/2308.09597)／[作者项目](https://github.com/LC1332/Chat-Haruhi-Suzumiya)

可借鉴的是：根据当前场景选择相关对白，让模型看到“这个人遇到这种情况如何接话”。它验证的是虚构人物角色扮演，不能充当普通真人复刻已成功的证据。

本项目可探索从用户确认的表达样例库中检索少量正例，同时避免把样例中的个人事实带给其他朋友。

### 4.3 TICL：记录哪里不像，以及本人会怎样改

TICL 在个性化写作中使用少量作者示例，并把失败回答和风格解释作为反馈，不更新模型权重。[NAACL 2025 论文](https://aclanthology.org/2025.findings-naacl.326/)

论文的限制很关键：部分小模型在初步实验中仍模仿标为坏例子的文本，长上下文理解是其方法的重要前提。[论文 PDF，Limitations](https://aclanthology.org/2025.findings-naacl.326.pdf)

本项目借鉴“原回复—本人改写—改写理由”的记录结构；实际推理优先尝试短规则和少量正例。是否放入反例应独立测试，不能照搬长提示，更不能将论文中的胜率解释成“像本人百分比”。

### 4.4 LaMP：先挑选相关个人资料

LaMP 研究检索个人资料再生成，在七项个性化任务中比较词面、语义和时间相关的检索方式。[ACL 2024 论文](https://aclanthology.org/2024.acl-long.399/)

这支持把“资料库”和“本轮实际送给模型的几条资料”分开设计。它不证明当前中文 4B 桌宠已能复刻用户，也不意味着必须采购向量数据库或调用云端 embedding。

### 4.5 两项补充研究与一个工程提醒

- 真实用户对话复现研究比较过用户画像结合 One-ID、LoRA 和全量微调，但使用的是日语、222M 参数的模型和专门数据集，不能直接转成当前 Qwen 模型的训练承诺。[原论文](https://arxiv.org/html/2409.00887v1)
- 一项覆盖四百余普通作者的研究发现，非正式博客、论坛风格比新闻、邮件更难模仿。这提醒我们把“没有 AI 腔”和“像特定本人”分别评分。[EMNLP 2025 论文](https://aclanthology.org/2025.findings-emnlp.532/)
- SillyTavern 的角色文档说明了角色设定、开场白、示例对白对上下文的影响。它是提示组织的工程参考，不能当成模型已完成训练的证明。[官方角色设计文档](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)

## 5. 推荐路线：先验证资料和提示，再决定是否微调

### 5.1 第一轮先做什么

维持已验证的 Qwen3-4B-Instruct-2507 和本地运行方式，拟开展小规模说话风格校准：

1. 收集有背景的本人真实回复，并由用户确认用途。
2. 从样例中整理少量明确规则，逐条让用户判断是否符合实际。
3. 在相同模型、参数、朋友记忆和历史条件下，比较当前人格、简短本人规则、规则加少量短正例。
4. 保存每条失败输出、本人改写和改写理由。
5. 用未参与修改的新题检查能否迁移；不能只用训练时的原题证明成功。

第一轮可通过现有编辑、发布、试聊和评估能力完成主要操作。若需要修改共通猫身份、增加提示可观测性或调整数据结构，必须先在正式 PLAN 写明差异；本研究不授权直接改代码。

### 5.2 第二轮再考虑示例检索

当固定少量示例无法覆盖场景时，再设计“场景—关系—相关真实表达”的检索。开始可以用标签和本地词面匹配，是否使用本地语义模型由实际失败决定。

当前项目已经存在朋友事实记忆检索，但没有创作者表达样例检索。不能把已有事实记忆功能描述成已经完成了风格 RAG，也不能把研究方案当作现成功能。

### 5.3 当前提示预算是具体限制

现有服务层把提示字符预算设为模型上下文参数的一半。在当前 numCtx=4096 时，两条消息内容合计只有 2048 个 JavaScript 字符单位。规则、人格 JSON、样例、用户输入、历史和记忆都占用这项预算；字符单位也不等于模型 token。[服务层预算](https://github.com/z-chenl/desktop_pet/blob/32f766ebb6826afb652a00887cab7e1b4aa8f4f4/src/main/service.ts)／[裁剪规则](https://github.com/z-chenl/desktop_pet/blob/32f766ebb6826afb652a00887cab7e1b4aa8f4f4/packages/persona-core/src/prompt.ts)

因此：

- 30–50 组样例指素材库规模，不是每轮全部发送。
- 每轮先尝试能容纳的少量短正例，具体数量由实际字符预算决定。
- 记录最终输入、被选样例和被省略的历史／记忆，防止“样例没送进去却判断方法无效”。
- 提高上下文或改预算会影响实现与性能，需要另列方案，不能只把数值调大就宣布解决。

### 5.4 微调的进入条件

当资料已经由用户确认、提示实际送达、仍反复出现稳定的表达差距时，才比较 LoRA／QLoRA。

Unsloth 已有精确 Qwen3-4B-Instruct-2507 的 bitsandbytes 4-bit Safetensors 版本，可作为训练候选；它不等于当前 Ollama 的 GGUF Q4_K_M 文件。[模型发布页](https://huggingface.co/unsloth/Qwen3-4B-Instruct-2507-unsloth-bnb-4bit)

当前 8GB 显存、16GB 内存可以列为实验条件，不能据此保证训练和导出成功。工具方也把显存要求标为估计，并说明上下文、模型与批次等会影响需求。[Unsloth 资源要求](https://unsloth.ai/docs/get-started/fine-tuning-for-beginners/unsloth-requirements.md)

未来路线应逐项验证：匹配基座和模板、训练适配器、合并／导出、导入 Ollama、再测风格与事实。Ollama 接受 GGUF 导入，不代表本机已验证了整个训练交付流程。[Unsloth 导出说明](https://unsloth.ai/docs/basics/inference-and-deployment/saving-to-ollama.md)／[Ollama 导入说明](https://docs.ollama.com/import)

微调成功运行、回答更像本人、事实可靠、朋友能部署，是四项独立结果。

## 6. 数据准备与反馈格式

### 6.1 首批建议规模

建议先整理 30–50 组开发样例，另准备约 15–20 个新场景作评估，其中保留一部分作最终验收。数量只是控制第一轮工作量的建议，不是保证效果的最低门槛。

优先覆盖：问候、分享进展、疲惫或烦躁、安慰、打趣、拒绝、意见不同、忙时简短回应、不知道的事实。区分熟朋友与普通朋友，不强行固定一种语气应对所有关系。

数据按完整对话或近似场景分组。相邻句子不能随机拆到开发集和验收集。评估题的参考回复不进入示例检索库；已经用于改提示的题转为开发题，另保留未见的新题。

### 6.2 每组样例模板

    样例编号：
    来源：真实历史／本人现场作答／本人改写
    对方关系：熟朋友／普通朋友／其他（不填真实姓名）
    场景与必要前文：
    对方说：
    我实际会说：
    我为什么这样接话：
    我不会采用的表达或分寸：
    使用范围：仅本地分析／允许进入共享角色
    数据用途：开发／开发验证／封存验收

只把用户本人的回复作为模仿目标。对方消息用于理解背景，不能把双方说话混成一个人。项目沟通中的条目化表达也不能未经用户确认就代表日常闲聊风格。

### 6.3 纠正记录示例

以下只示范记录方式，不声称建议回复已经像用户：

    原问题：我的验证饮料代号是什么
    模型回答：答出 LM_R_青梅 后追加口味和分享建议
    问题标签：多余建议；回答超出问题
    本人改写：由用户填写
    改写理由：由用户说明何时简答、何时会继续接话
    可先验证的事实约束：只回答已知代号，不补充口味或共同经历

对于“我的小猫好调皮”，可以让用户自己写实际会接的话，再标记是追问、玩笑、共情还是仅一句回应。由 AI 代写一大批“你的风格”再拿来学习，会失去真实风格参照，不作为首批语料来源。

### 6.4 共享规则

朋友收到的是经用户发布的角色版本。朋友聊天可产生自己的记忆，但不自动改写创作者风格。

共享角色只包含用户批准分享的规则、表达样例和未来可能的模型配置／权重信息；原始聊天、联系方式、私人事实、朋友数据库和封存评估集继续单独保存。样例展示怎么说话，不给模型凭空增加个人经历。

公开 GitHub 适合保存代码、计划、研究来源、匿名统计和脱敏问题记录。真实聊天与本人的私密样例不因“严格记录”而自动公开。

## 7. 评估方法：怎样知道它有进步

| 维度 | 谁判断、怎样记录 |
| --- | --- |
| 本人风格 | 用户看匿名排列的回复，判断自己是否会这样说；允许多种正确说法 |
| 自然程度 | 是否像日常接话，是否机械完整、套话过多或总要讲道理 |
| 关系分寸 | 是否出现没有依据的亲昵称呼、撒娇、共同经历或身份假设 |
| 事实依据 | 有没有把已知事实说错、把样例事实移植给当前朋友、在不知道时编造 |
| 意图匹配 | 是否不必要地追加建议、追问、安慰或把任何话题转成猫日常 |
| 多轮稳定性 | 数段 3–5 轮新对话后是否回到通用 AI 腔；是否记错主体 |
| 速度与上下文 | 记录完整回复等待、实际提示范围、遗漏量；不只报告热身后的最短一轮 |

建议由用户在看模型输出前写一部分参考回复，再进行匿名对比。固定模型和参数；各组使用相同空历史或同一固定历史，朋友记忆条件一致。保留差的输出，不只挑最佳样例展示。

先按“多少题更像、多少题存在多余建议、多少题编造”报告，不把少量主观评分包装成精确的“人格相似度百分比”。具体通过门槛在正式 PLAN 中与用户约定，研究稿不预先宣布达标。
