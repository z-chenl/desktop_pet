# 开发、审核与交接

## 功能版本

1. Chat 整理方案草稿。Codex 在版本分支建 `docs/iterations/<版本>/`，提交 PLAN 并交给 Work。
2. Work 按指定提交审核方案，给出报告。需要修订时，由 Codex 留存原意见、记录修订号与差异，交回相应审核。用户对已展示的明确修订及范围作决定。
3. Codex 保存用户确认原话、对应版本和修订、所批准范围及可得的时间或消息依据。自然语言确认有效。批准后连续实现、验证、修复、更新记录和提交。
4. Work 审核指定的完整实现提交和证据。Codex 保存原报告，另记整改；改动代码、依赖、运行配置或验收要求，交回复核。仅归档报告和日志可形成记录提交，保留原审核目标。
5. 用户验收实际效果。Codex 依据已有权限通过 PR 合并并归档版本；合并、标签或发布所需的授权缺失时，交用户决定。

范围扩大、验收标准改变、重大技术或数据处理变化、未批准费用，先说明影响并取得对应决定。已有授权内的常规操作连续完成。

## 三份迭代记录

- **PLAN.md** 写明修订、目标和基线、范围与排除项、任务编号、设计、模块与接口，以及模型、人格、记忆、数据和配置变化。列出验收标准、检查与环境、费用与下载、外部服务与操作权限、风险、数据迁移、备份恢复、用户批准依据与待确认项。
- **WORKLOG.md** 按任务节点记编号、目的、变更、验证方法与结果、环境、问题、提交或同步情况、下一步。保留影响选择或排查的失败。已有历史验证须注明出处；本次实测注明系统、模拟或真实模型及未覆盖项。
- **REVIEW.md** 绑定被审提交的完整编号，保存 Work 原文和用户验收依据。未收到报告时写“待审核”。整改说明、实现者自测、用户批准各自注明作者和对象。

[STATUS](STATUS.md) 只维护现阶段、相关分支与提交、审核、阻塞和下一步。记录提交可引用先前的实现、审核目标及交接卡中的同步结果。

## Git 与数据

Codex 统一提交、推送。按明确任务节点暂存本次路径，检查差异和文件清单，分别确认本地保存、提交、远程分支指针。同步失败时保留提交并记下原因及待推送范围。保留其他会话和用户改动；普通同步问题不使用强推、工作区重置、清空目录或可见性变更。

密钥、个人数据库、私人聊天、模型缓存、依赖目录和整个历史对话均留在版本控制之外。按变更风险验证，优先使用隔离的测试数据。空仓库首次推送 main 的授权仅见 [BOOTSTRAP r1](iterations/BOOTSTRAP/PLAN.md)。

## 交接卡

每次交付写明仓库、阶段和任务编号，实际路径与分支，完整目标提交及远程核实结果，PLAN 位置、修订和批准依据，完成内容，验证环境、方法、结果和证据位置，未验证项或阻塞，以及下一角色和具体任务。
